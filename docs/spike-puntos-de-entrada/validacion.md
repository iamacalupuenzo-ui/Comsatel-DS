# ¿Qué debe migrar FleetOperations para aprovechar la reducción inicial?

## En 30 segundos

**Veredicto: aprobado con ajustes.** El plan de tamaño y compatibilidad se cumple: el subpath baja el aporte de la librería a `main` de 626.634 a 28.726 bytes, y el inicial de 1,03 MB a 530,21 kB. El import raíz mantiene los símbolos y compila, pero vuelve a incluir 626.731 bytes; publicar parece compatible con el workflow actual, aunque conviene reforzar la resolución local de tipos antes de escalar.

## Hallazgos

1. **`tsconfig.json:9-11` — mapeo local de dos destinos.** La medición demuestra que esbuild usa el primer `.mjs`; la compilación Angular de este sitio también acepta las declaraciones del segundo destino. Es válido en este montaje, pero frágil: los nombres y estructura internos `fesm2022/` y `types/` son artefactos del build, podrían variar con ng-packagr, y TypeScript podría seleccionar `.mjs` como sustituto de `.d.mts` si cambia el orden/resolvedor. Para escalar, conviene que `paths` apunte primero al paquete `dist/comsatel-ds/icons` (y equivalentes) para que NodeNext/bundler interprete `exports.types` y `exports.default`; validar esa opción en este repo y mantener las rutas internas solo si la configuración de build realmente las necesita.

2. **`projects/comsatel-ds/src/public-api.ts:7,30,84` — ciclo raíz ↔ secundario potencial.** La raíz reexporta cada subpath y estos, por ahora, no importan desde la raíz: no aparece ciclo en estas entradas. Sin embargo, las rutas `paths` del root solo mapean el paquete raíz; las entradas que se agreguen deben importar dependencias por subpath o ruta interna permitida, nunca desde la raíz. Mantener una regla automatizada que detecte imports `@iamacalupuenzo-ui/comsatel-ds` sin sufijo en entradas secundarias.

3. **`projects/comsatel-ds/src/public-api.ts:7,30,84` — el import raíz conserva compatibilidad, no ahorro.** La salida DTS raíz reexporta tipos desde `/icons`; `/motion` y `/input` están presentes como reexports del root. La medición de raíz es 626.731 bytes, esencialmente igual a baseline 626.634. FleetOperations debe cambiar imports de símbolos del shell a `@iamacalupuenzo-ui/comsatel-ds/icons` y `/motion` para reducir el arranque; cambiar imports de páginas lazy no es requisito para este ahorro inicial.

4. **`projects/comsatel-ds/icons/src/icon.ts:22`, `projects/comsatel-ds/motion/src/press-scale.directive.ts:16`, `projects/comsatel-ds/input/src/input-group-clear.ts:17` — fuentes únicas y dependencia entre entradas.** `git diff --name-status` reconoce los movimientos como renombres, y `rg` encuentra una sola definición fuente por clase. Los FESM secundarios contienen `Icon`, `PressScale` e `InputGroupClear`; la entrada `/input` importa `Icon` desde `/icons`, sin copiar su definición. `dist/.../types/*` también publica declaraciones separadas para las tres clases.

5. **`tsconfig.json:9-11` — raíz para los tres símbolos compilada.** En el estado de la rama, `src/app/pages/input-demo/input-page.ts:2-14` obtiene `Icon` desde raíz y `:16` prueba `InputGroupClear` desde `/input`; `src/app/layout/shell/shell.ts` usa `Icon` y `PressScale` por subpaths. La variante de medición de raíz conserva los imports del shell desde el package root y compiló con 626.731 bytes. `PressScale` se conserva en la entrada raíz, y la declaración raíz usa exportaciones transitivas para `Icon` e `InputGroupClear`.

6. **`guidelines/icon.md`, `guidelines/directives.md`, `guidelines/input.md`, `guidelines/motion.md` — rutas de guías.** Las rutas generadas siguen los nuevos directorios de fuente; `scripts/lib/ds.mjs:75-92` sigue reexports públicos hacia las fuentes secundarias y continúa recorriendo el resto bajo `src/lib`. Las historias quedan donde Storybook las descubre en `.storybook/main.ts`, aunque la historia de `PressScale` mantiene un nombre de ruta antiguo en comentario, no un import roto. La evidencia reportada de `check:docs`, tests, audit y Storybook respalda el ajuste; los errores de Compodoc son preexistentes según la comparación indicada.

7. **`.github/workflows/publish-package.yml:30-54` — publicación compatible con lo probado.** El workflow instala, ejecuta `check:docs`, `build:lib`, `test:ci`, Storybook y audit; el `pack.log` muestra los tres FESM, los tres `.d.ts`, el manifiesto y CSS. `scripts/package-style.mjs:15-23` conserva claves `exports` de ng-packagr y añade `./styles.css`. No se ejecutó ni publicó. A escala, el workflow no verifica explícitamente `pack:lib` ni la presencia de cada export; agregar esa aserción haría detectable una regresión antes de publicar.

8. **Medición del plan — criterios cuantitativos.** Con la definición fija de `measure.js`: baseline root `main` 626.634 bytes e inicial 1,03 MB; subpaths construidos pero import raíz 626.731 bytes e inicial 1,03 MB; imports secundarios `main` 28.726 bytes e inicial 530,21 kB. La meta de ≤200.000 y menos de 1 MB se cumple holgadamente solo con los imports secundarios. El `sub-stats.json` muestra el FESM raíz y el de input en chunks no iniciales; no hay duplicación de definiciones detectada.

9. **`projects/comsatel-ds/icons/`, `motion/`, `input/` — movimiento de fuentes.** ng-packagr rechazó las fuentes fuera del directorio de cada entrada (`TS6059`, según la evidencia del constructor), por eso los renombres son una adaptación necesaria. Riesgo de escala: historias, recursos relativos y comentarios de ruta pueden quedar desfasados aunque el build principal pase. Cada migración debe actualizar imports de templates/estilos/historias, hacer que el generador de guías resuelva exports transitivos y revisar cobertura de docs para que cada símbolo público siga documentado.

## Recomendación y orden

No migres las 57 carpetas en una sola tanda. El spike prueba que los puntos secundarios sirven cuando el consumidor importa explícitamente desde ellos; no ofrece ahorro automático para quien conserva el root import. Orden sugerido: **(1)** FleetOperations cambia primero solo los imports del shell y mide su bundle; **(2)** validar una ruta TypeScript más estable vía `exports` en `package.json` frente a los paths a artefactos; **(3)** escalar por familias pequeñas de componentes con dependencias internas explícitas y chequeo de ciclos; **(4)** al final mover las carpetas con mayor beneficio medido, y añadir una verificación del tarball al workflow.
